Hugo im Codespace lokal testen und veröffentlichen

24. September 2026·3 mins

Voraussetzungen #

Dieses Repository enthält die Hugo-Website im Unterordner whoami. Die folgenden Befehle werden daher aus dem Repository-Hauptverzeichnis ausgeführt. Nach dem Erstellen eines neuen Codespaces müssen im Hugo-Verzeichnis zunächst die Go-Module eingerichtet werden:

cd whoami
hugo mod tidy

Hugo im Codespace starten #

Zum Testen der Website startet man den Hugo-Entwicklungsserver mit:

hugo server -D --bind 0.0.0.0 --port 1313

Die Optionen haben folgende Bedeutung:

  • server startet den Entwicklungsserver.
  • -D (--buildDrafts) nimmt auch Beiträge mit draft = true in die Vorschau auf.
  • --bind 0.0.0.0 macht den Server innerhalb des Codespaces erreichbar. Eine Bind-Adresse wie 127.0.0.1 wäre nur innerhalb des Codespaces erreichbar.
  • --port 1313 verwendet den üblichen Hugo-Port.

Der Server bleibt im Terminal aktiv. Zum Beenden genügt Ctrl+C.

Port zum lokalen Rechner weiterleiten #

In einem zweiten lokalen Terminal wird der Port des Codespaces weitergeleitet:

gh codespace ports forward 1313:1313 --codespace "$CSname"

Dabei steht der erste Port für den lokalen Rechner und der zweite für den Codespace. $CSname muss den Namen des gewünschten Codespaces enthalten, zum Beispiel:

CSname="mein-codespace"
gh codespace ports forward 1313:1313 --codespace "$CSname"

Anschließend ist die Vorschau unter http://localhost:1313 erreichbar. Der Bind-Befehl und die Portweiterleitung gehören zusammen: Hugo muss auf 0.0.0.0 lauschen, damit die Weiterleitung den Server erreicht.

Deployment-Script ausführen #

Das Script gh-nofind.sh wird aus dem Repository-Hauptverzeichnis gestartet:

./gh-nofind.sh

Falls die Datei noch nicht ausführbar ist, kann die Berechtigung einmalig gesetzt werden:

chmod +x gh-nofind.sh

Was das Script macht #

Das Script besteht aus zwei Teilen. Zuerst wird die Website gebaut:

cd whoami
rm -rf public
hugo --minify
cd ..

Es wechselt in das Hugo-Arbeitsverzeichnis, entfernt den alten Ausgabeordner und erzeugt mit hugo --minify eine minimierte Version der Website in whoami/public.

Danach werden die erzeugten Dateien in einem temporären Ordner gesichert und der Veröffentlichungsbranch vorbereitet:

rm -rf ../temp_site_deploy
mkdir ../temp_site_deploy
cp -r whoami/public/* ../temp_site_deploy/
git checkout gh-page

Die Dateien aus public werden zwischengespeichert, weil anschließend der Inhalt des Branches gh-page ersetzt wird. Das Script löscht dort die vorhandenen versionierten Dateien, kopiert den neuen Build in das Branch-Root-Verzeichnis und legt .nojekyll an. Dadurch versucht GitHub Pages nicht, die Ausgabe zusätzlich mit Jekyll zu verarbeiten.

Zum Schluss wird der neue Stand veröffentlicht und wieder zum Arbeitsbranch gewechselt:

git add .
git commit -m "Deploy: Update site content"
git push origin gh-page
git checkout master
rm -rf ../temp_site_deploy

Der Branch gh-page enthält damit direkt die fertigen HTML-, CSS- und JavaScript-Dateien, während der Quellcode und das Hugo-Projekt im Branch master bleiben.

Vor dem Deployment beachten #

Das Script arbeitet mit git checkout, löscht Build-Dateien und ersetzt den Inhalt des Veröffentlichungsbranches. Deshalb sollten Änderungen vorher committet oder anderweitig gesichert werden. Außerdem muss der aktuelle Branch master heißen und der Remote origin auf das GitHub-Repository zeigen.
